一、评估范围与方法 Scope & Method

评估对象为 POC 一期交付物，覆盖后端服务、前端三端（管理端 / 用户端 / NOC 大屏）、K8s 集成层与部署形态。方法为：

  1. 代码走查：逐模块检查鉴权、事务、状态机与异常路径；
  2. 实测验证：在真实 k3s 集群（v1.31.4）上跑通下单、调度、配额、回收、对账全链路；
  3. 对照验收：以 40 条需求清单（P0 21 / P1 12 / P2 7）逐条核对；
  4. 风险识别：按「是否阻断生产」分级，而非按开发工作量分级。
本报告中的性能与容量结论标注为「经验判断」的条目，均未经过压测，不得作为容量承诺使用。

二、架构评估 Architecture

2.1 分层结构

层实现评估
接入层Nginx / 直连 8099，静态页 + REST缺 TLS 与 WAF
应用层Spring Boot 3.4 单体，75 个接口，分层 Controller/Service/Db结构清晰，可维护
集成层K8sClient 接口 + FakeK8s/RealK8s 双实现（fabric8）可替换，切换零改业务
数据层PostgreSQL 16，18 张表，幂等建表 + 空库种子重启不丢数据
底座k3s v1.31.4；平台自身以 Deployment + ServiceAccount 部署进集群两层均在集群内

2.2 关键设计判断

决策选择理由与代价
底座是否自研 不自研，用原生 K8s 客户可 kubectl、可 Helm、不锁定；代价是无法做深度定制调度，需依赖 Volcano 等外部组件
租户隔离方式 Namespace + ResourceQuota K8s 原生硬限制，apiserver 层拦截，不依赖应用层判断；代价是配额粒度只能到卡数，做不到显存级
会话方案 DB 会话表 + Bearer Token 可服务端强制下线、可审计在线会话；代价是每次请求多一次 DB 查询（当前规模无感）
K8s 接入方式 接口抽象 + 双实现 无集群也能演示，有集群自动切真；代价是多一层间接，排查时需确认当前 mode
结论：架构上没有明显缺陷。真正的问题不在设计，而在部署形态与可观测能力——见第五节。

四、技术风险清单 Risk Register

按「是否阻断生产上线」分级，不按开发工作量分级。

P0 · 阻断生产（已闭环 4 项 / 未闭环 2 项）

#风险后果处置结果
1全链路单副本应用、数据库、控制面均为单实例；任一进程崩溃即全站不可用，无自动接管未闭环 需应用 ≥2 副本 + PDB、PG 主备、控制面 3 节点
2无 TLSHTTP 明文传输，登录密码与 Bearer Token 可被同网段嗅探已闭环 nginx 1.27 终止 TLS，80→443 强制跳转，已配 HSTS 与安全响应头
3无备份与恢复演练数据库损坏或误删即不可恢复；无 RPO/RTO 定义已闭环 pg_dump -Fc 每 24 小时一次，保留 7 天，已生成并校验首份备份
4无真实监控告警故障靠用户报障发现；指标为模拟数据，不能反映真实状态已闭环 Prometheus + Grafana + node-exporter；业务 Gauge 已暴露，仪表盘自动加载
5无私有镜像仓库Pod 镜像为占位（busybox），客户业务镜像无来源；离线环境无法交付已闭环 registry:2，push/pull 已验证，可作离线镜像中转
6调度策略未验证Gang / 抢占 / 队列均未真实生效，分布式训练场景可能死锁未闭环 需部署 Volcano（当前网络无法拉取官方清单）

  • 网络：节点互通，GPU 节点建议万兆；多机训练需 RDMA 交换机预留
  • 软件源：内网需提供镜像仓库或允许离线导入（当前镜像 552MB）

  • 账号：GPU Operator、Volcano 等组件的离线包获取渠道

九、结论与建议 Conclusion

可以拿去演示，不能拿去上线。

当前状态适合：技术验证、POC 演示、客户方案汇报、二期立项依据。

不适合：直接承载生产流量、对外承诺 SLA、通过等保测评。
