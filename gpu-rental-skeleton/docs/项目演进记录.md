### 阶段 1 · 用脚本把 K8s 层验穿（11-02 21:08–21:37）

`k8s-demo/` 四个脚本，目标只有一个：**在没有显卡的机器上证明调度与配额是真的**。

核心手法一句话：

```bash
kubectl patch node <node> --subresource=status --type=json -p='[
  {"op":"add","path":"/status/capacity/nvidia.com~1gpu","value":"8"},
  {"op":"add","path":"/status/allocatable/nvidia.com~1gpu","value":"8"}
]'
```

device plugin 本来就是把卡写进 Node status 的 capacity/allocatable，调度器只读这个字段——**直接 patch 它，调度行为与真卡完全一致**，唯一区别是容器里没有 GPU 设备文件。

当晚实测三件事，全过：

| 验证 | 结果 | 证据 |
|---|---|---|
| 分配生效 | Pod 落到节点 Running | `Successfully assigned tenant-a/gpu-test-1 to ee...` |
| 租户配额 | 第 5 个被拒 | `exceeded quota: gpu-quota, requested 1, used 4, limited 4` |
| 容量耗尽 | 第 9 个 Pending | `1 Insufficient nvidia.com/gpu` |

**这一步是整个项目的地基**：先证明"K8s 真能按租户分卡"，再谈上层平台。顺序反了会写出一堆自欺欺人的 UI。

### 阶段 2 · 平台落地并接真集群（11-02 晚 → 11-03）

`gpu-rental-skeleton/` 从骨架长成三端应用（用户端 / 管理端 / 大屏），11-02 的记录里已经有这条链路：

## 三、六个关键决策

每个都写成「问题 → 选择 → 为什么 → 被否的方案」。

### 1. K8s 客户端做成接口，两套实现

**问题**：开发机没有 GPU、没有集群，业务逻辑怎么写？

**选择**：`K8sClient` 接口，`FakeK8s`（模拟 3 秒就绪、可模拟 Terminating 卡住）与 `RealK8s`（fabric8 连 apiserver），按 `rental.k8s.mode` 切换。

**为什么**：业务层、计费、回收一行不用改就能在两种运行时之间切。这也是为什么"接真集群"这件事的成本只有**一个类**——README 原话："业务层、计费、回收逻辑一行不用改"。

**被否的**：直接写 fabric8 调用。代价是没集群时整个项目跑不起来，前端没法开发。

### 2. 占卡用条件更新，不用分布式锁

**问题**：并发下单不能一卡两卖。

**选择**：

```sql
UPDATE gpus SET status='occupied', instance_id=? WHERE id=? AND status='free'
```

受影响行数 != 申请卡数就抛异常、整个事务回滚（`RentalService.createOrder`）。

**为什么**：行级条件更新本身就是原子的，数据库已经把并发问题解决了。上 Redis 分布式锁，等于在数据库之外再造一套一致性，多一个故障点、多一次网络往返。

**代价**：必须在事务里；这也是为什么"占卡 + 建单 + 建实例 + 扣款"绑在同一个 `TransactionTemplate` 里。

### 3. 下单事务只包数据库，K8s 调用放提交之后

**问题**：建 Pod 是外部调用，不能放进数据库事务（可能几十秒，还会阻塞连接）。

**选择**：事务内只做占卡/建单/建实例/扣款；事务提交后再调 `k8s.create()`，失败则补偿——实例置 `failed`、释放占用的卡、抛业务异常（代码注释：真实系统要 outbox，这里 try-catch 补偿逻辑等价）。

**为什么**：先保证账本自洽，再处理外部副作用。顺序反了会出现"Pod 建了但订单没落库"——这种脏数据没法对账。

**已知欠账**：进程在"提交成功、调用 K8s 前"崩溃，会留下占着卡但没有 Pod 的实例。现在靠 `Reconciler` 和资源对账兜，不是严格意义上的 outbox。

### 4. 释放顺序：先删 Pod，成功后才改库

**问题**：释放时先改库还是先删 Pod？

**选择**：先 `k8s.delete()`，返回没删干净就把实例置 `releasing` 并报错，交给巡检重试；真删掉了才结算 + 释放卡（`RentalService.release`）。

**为什么**：代码注释写得很直白——反过来会「账面已释放、卡还占着」。那是最坏的状态：客户已经不付钱了，卡还在被占，且系统认为一切正常。

**代价**：会短暂出现"钱已经按秒在算、但实例显示回收中"。这是主动选择的：**宁可账面对不上，也不能资源泄漏**。

### 5. 幂等靠唯一约束 + 并发回查

**问题**：用户连点两次下单，或者网络重试。

**选择**：`orders.order_no` 唯一约束；事务内撞 `BizException` 后**回查一次** `orderByNo`，查到就返回原订单（`RentalService` 144–152 行）。

**为什么**：只做前置查询挡不住并发——两个请求可能同时通过检查，然后一个成功一个撞唯一约束。回查这一步，把"撞约束"从异常翻译成"幂等命中"。

**这是这个项目里最值得讲的一段代码**：它承认了检查与写入之间有窗口，然后兜住了。

### 6. 对外租赁关闭抢占与借用

**问题**：Volcano / Kueue 有抢占和配额借用，开不开？

**选择**：不开。`settings.scheduler.preempt_tenant = false`，`k8s-demo/README` 写明"借用、抢占未验证"且**不应开启**。

**为什么**：原文一句——"客户配额被借走 = 违约"。技术能力有，商业上不能用。这条决策体现的是：**能开和该开是两件事**。

顺带一条调度策略：单卡订单 bin-packing（优先塞已占用节点），把整台空机留给整机订单（`Db.pickSingleGpuIds` + `pickWholeNode` 的 `GROUP BY node_id HAVING COUNT(*) >= 8`）。

| 1 | 宿主机 `kubectl` 报 **Bad Gateway** | `kubeconfig` 的 server 是 `host.docker.internal:6443`，给容器内用的；宿主机解析不了 | 宿主机用 `kubeconfig-local` | 会。两个文件名字太像，交接必须说清 |
| 2 | patch 的 8 卡过一阵消失 | kubelet 周期性回写 Node status，覆盖手工字段 | 重跑 `01-setup.sh` 的 patch 段 | 会。这是伪造容量的固有代价 |

## 六、尚未闭环（按严重度）

### P0 · 不解决就不能叫生产

1. **没有真卡**。GPU 温度/功耗/利用率是正弦波 + 固定种子生成的；`nvidia-smi` 跑不了。→ 需 GPU Operator + DCGM exporter。
2. **没有支付**。只有余额预扣，没有充值通道、没有对账文件、没有发票。
3. **告警不外发**。只在界面里 ack/resolve，没接短信/企微/邮件。值班的人不看屏幕就等于没有告警。
4. **集群信息硬编码**。`settings.cluster.*` 是种子值，与真实 apiserver 不一致（v1.34.1 vs v1.31.4）。→ 应加一个 `GET /api/admin/cluster-info` 现读 `/version`、`/api/v1/nodes`。

### P1 · 影响交付质量

5. **GPU 切分未验证**（1/2、1/4 卡）。需 HAMi + 真卡，5090 新架构支持未知。
6. **Volcano 未安装**，Gang / 队列配额 / 抢占全部未实测——所以这些能力在界面上有入口，但没有实证。
7. **SSH / Jupyter 是演示值**：公钥是拼出来的，密码生成了但没落到容器。
8. **Pod 日志是确定性生成的**（按 Pod 名哈希）。
9. **单节点，无 HA**。数据库、应用都单副本，节点挂了全挂。
10. **无 NetworkPolicy**。租户命名空间之间网络没有隔离。
11. **审计无防篡改**。审计表可被有库权限的人删改，不满足严格合规。

### P2 · 优化项

12. **0 自动化测试**。全靠手动跑流程 + `kubectl` 核对。`RentalService` 的并发与幂等逻辑，最该有测试。
13. **前端单文件**：`admin.html` 1319 行，改一个模块要通读全文件。
14. **单价双源**：常量 + settings 表，改了不生效（坑 #7）。
15. **`Db.java` 652 行手写 JDBC**，SQL 与业务混在一起，改表结构容易漏。

## 七、交接须知（30 秒上手）

```bash
cd D:/code/hailanyun-20261102/gpu-rental-skeleton

# 起（Docker，完整栈）
mvn -DskipTests package && docker compose up -d --build
# 打开 https://localhost   admin / Hly@2026

# 只跑应用（H2 内存库，无需 Docker）
java -jar dist/gpu-rental-0.1.0.jar

# 平台部署进集群（客户形态）
kubectl apply -f deploy/k8s/tokenark.yaml
```

**三个必须知道的点**：

1. `docker-compose.yml` 里 `RENTAL_K8S_MODE=real`，没集群就改 `fake`，否则起不来。
2. `k8s-demo/kubeconfig` 是**容器内**用的（`host.docker.internal`）；**宿主机用 `kubeconfig-local`**。
3. `DbBootstrap` 只在空库时灌种子；想重置演示数据，得清库（或删 `pgdata` 卷）。

**改代码先看这三个类**：

| 类 | 职责 | 改它会影响 |
|---|---|---|
| `RentalService` | 下单、释放、结算 | 账本正确性，最不能乱动 |
| `K8sClient` / `RealK8s` | 集群交互 | 真集群链路 |
| `AuthInterceptor` | 接口鉴权 | 所有 `/api/**` 的访问 |
