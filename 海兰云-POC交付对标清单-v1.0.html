一 · 三条结论

1. POC 不等于生产交付。成功标准写的是"技术接口人确认闭环成立"，风险项写的是"用示例租户演示、数据标注为演示数据"。所以 POC 的目标是让接口人点头，不是上线收钱。四个 P0 真跑起来，三个 P1 用示例数据演完整，就够了。

2. 调度器选 Volcano，不选 Kueue。需求 3 明确要 Bin-packing、Spread、Gang、队列优先级抢占四项。Kueue 只解决配额与抢占（且是准入层，不管调度），Volcano 一个组件全覆盖。只装一个，少学一套。

3. 切分（需求 4）先留口不落地。5090 无 MIG，HAMi 对新架构的支持尚未验证。POC 阶段用时间片共享演示 + 数据模型预留切分字段，真上切分等卡型确认后再做。

二 · 八条需求逐条对标

#需求点优先级 现有原型POC 做什么生产化还差什么人天
1K8s 原生底座P0有界面 k3s 集群（2 或 3 节点）；Pod / Deployment / Namespace / Label / Taint / ResourceQuota 全部可查看与操作 多控制面 HA（3 server 起）、升级与回滚流程1
2GPU 算力纳管P0有界面 GPU Operator 纳管全部卡；DCGM 上报利用率/显存/温度/功耗；节点上下线可操作 异构卡型适配（后续更高规格）、驱动版本矩阵1.5
3GPU 调度P0仅界面 Volcano：队列 + 优先级 + 抢占 + Gang（2 Pod 同起同停） + Bin-packing（同节点装满） 按租户/机架的拓扑感知、抢占策略调优、跨队列借用（默认关闭）2
4GPU 共享切分P1仅界面 用 GPU Operator time-slicing 做时间片共享演示；MIG/vGPU 仅做能力探测，不做承诺 HAMi 落地（须先验证新架构 sm120 / CUDA 版本支持）、切分粒度与计费口径1
5集群监控P0有界面 Prometheus + DCGM 接真数据，替换原型里的写死数据；监控页与大屏同源 长期存储、告警分级、多集群聚合2
6多租户与租赁运营P1运营视角 示例租户 + 租户自助申请页 + 实例交付 + API Key + 卡时计量与账单（演示数据，页面标注） 真实计费、账单、对账、支付；合同与配额审批流5
7告警与巡检P1仅界面 4 条阈值告警（XID 非 0 / 温度 >85 / 显存 >95% / 节点 NotReady）+ 规则版巡检报告 日志审计、自愈动作（需人工确认）、LLM 诊断可后续叠加1.5
8高可用与演进P1无 POC 以 3 控制节点部署示意（若客户只给 2 台则仅展示单控制面 + 说明路径） 真 HA、平滑扩容、卡型演进方案0.5
POC 合计（含演示数据构造与联调彩排）≈ 14

采购后再补 P1 的生产化部分（真实计费与账单、切分落地、HA），追加约 15 人天。不建议把两步合成一次报价——客户预算敏感，先给能验证的小闭环。

三 · POC 两周节奏

天动作当天必须看到的证据
D1宿主机装 NVIDIA 驱动，组 k3s 集群nvidia-smi 出卡；kubectl get nodes 全 Ready
D2装 GPU Operator（关闭自带驱动安装）每节点 nvidia.com/gpu 可分配数正确
D3装 Volcano，建队列与优先级，跑通 gang2 个 Pod 要么同时起、要么都不起
D4Prometheus + DCGM 接入每张卡有实时曲线，序列数等于卡数
D5卡池页接真数据（替换写死数据）关掉一台节点的 kubelet，页面 30 秒内变红
D6租户 + Namespace + ResourceQuota租户超额后第 N+1 个 Pod 起不来
D7实例交付链路：申请 → 创建 → 连接入口点一次，90 秒内拿到可用实例
D8卡时计量与账单页（演示数据）页面数字与实例时长一致，且明确标注"演示"
D9告警规则 + 巡检报告制造一次高温或掉卡，收到告警
D10大屏接真数据 + 全流程彩排10 分钟演示一遍不卡壳

四 · 演示脚本（10 分钟）

01
集群总览
一句话定调："这套是 K8s 原生，下面每一个对象都能用 kubectl 管。"
30 秒
02
节点管理 · 打开 YAML 抽屉
展示标准 Node 对象与 Label/Taint，执行一次 Cordon，现场看到不可调度。

03
GPU 资源池 · 跑一个 gang 任务
同时提交 2 个 Pod，展示"要么一起上、要么都不上"。这是需求 3 最硬的一条。

04
工作负载 · 看调度事件
说明不是封装的假界面，Pod 的调度过程可追溯。

05

走完一个租户从申请到拿到卡的完整闭环，明确说明"计费为演示数据"。
2.5 分钟
06
监控与告警
真数据曲线 + 现场触发一条告警，证明不是截图。
1.5 分钟
07
大屏
投屏演示，给领导看的那一页。
30 秒
08
收尾三句话
"底座是你们要的 K8s 原生，上层是能赚钱的调度与租赁，规模从 2 台到 72 卡不用重做。"
1 分钟

五 · 必须先确认的五件事

两个矛盾，会直接改变工作量

  1. 规模到底是 72 卡还是 16 卡？售前交流说"现有 2 台 5090 测试"，需求文档写"生产集群 3 控制节点 + 9 工作节点共 72 卡"。差 3 倍工作量，且决定 HA 是不是 P0。
  2. 切分做不做？口头说"不做微切分没必要"，书面需求 4 列 P1"提升单卡出租率"。建议按书面准备、按口头谈范围。

三个环境前提，不给就停工

  1. 集群访问权限：root 还是 sudo，能否直连
  2. OS 与内核版本：5090 需要较新内核，版本不足要先升级（隐藏工期）
  3. 能否出外网：决定是否需要准备离线安装包（约 5–8 GB，需提前一天准备）

六 · 风险与应对

风险（需求文档已列）我们的应对
客户纠结 K8s 细节主动展示，不隐藏。每个页面都留 YAML 抽屉与 kubectl 等价命令，让接口人确认"这是真 K8s，不是套壳"
预算低，要求分批POC 报价与生产化报价分开；POC 只做四个 P0 加演示级 P1，约 14 人天
无真实租户用示例租户演示完整闭环，所有演示数据在页面上打"演示"标记，避免验收争议
HAMi 对新架构支持未验证POC 不承诺切分能力，只做时间片演示；切分列入采购后评估项
2 台机器无法做真 HA如实说明：控制面高可用需 3 节点，若只有 2 台则展示部署路径与扩容方案，不承诺 SLA
