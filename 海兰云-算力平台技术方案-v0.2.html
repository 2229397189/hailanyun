0 · 一页结论

我们卖的不是一个"平台"，是一套"能让卡马上租出去并收到钱"的最小闭环。

60 天只做四件事：卡能分配、租户能隔离、订单能计费、客户能自助。调度、监控、容器、镜像全部用成熟开源，不自研。

三个必须让客户记住的点：

  1. 不做 GPU 切分——5090 本身不支持 MIG，客户也明确说不需要，这块最贵的成本直接不存在。
  2. 60 天出的是能收钱的卡池，不是 PPT 架构——第 8 周演示"下单→拿卡→跑任务→出账单"完整链路。
  3. 第三阶段的 Token 平台不用重做——账户、额度、计费、模型网关已有在跑的版本，第一阶段建的账户以后直接接着用。

4 · 开源选型

结论先说：没有一套现成开源能直接当"算力租赁平台"卖。能直接用开源顶上的是调度、监控、容器、镜像这几层；订单、计费、租户开通必须自己写——这三块恰好是和客户账户体系绑死、也是最愿意付钱的部分。

组件许可证在我们方案里的角色为什么不选替代品
Kubernetes / k3sApache-2.0统一资源底座，客户已认可OpenStack 体量过大，2 台机器跑不动也用不上
NVIDIA GPU OperatorApache-2.0驱动、容器运行时、Device Plugin 一键纳管手装驱动在 2 台以上就无法维护
VolcanoApache-2.0队列配额、gang scheduling，为 P2 多机预留默认调度器不支持队列与组调度
Prometheus + DCGM ExporterApache-2.0GPU 指标采集与告警的事实标准自研采集器成本高且拿不到 XID / ECC
GrafanaAGPL-3.0运维看板；对外大屏建议自研单页AGPL 只部署不改源码即可，但对外产品化时规避
JupyterHubBSD-3租户开箱即用的开发环境自研 Notebook 编排不划算
HarborApache-2.0租户私有镜像仓库—
KubeVirtApache-2.0仅当客户要求"给整机 / 给 Root 虚拟机"时启用P1 默认给容器，虚拟机按需开启

关于 "开源包一下就能卖"

能做，但要说清包的是哪一层。调度器和监控是"零件"，谁都拿得到，卖不出价；客户付钱买的是计费准不准、回收干不干净、出问题谁兜。所以我们的做法是：零件全用开源省时间，把 60 天花在业务层和稳定性上。

6 · 明确不做的范围

不做的事原因
GPU 微切分 / vGPU / MIG5090 硬件不支持 MIG；客户明确不需要；做了也没有收益
RDMA 多机分布式训练调度属于 P2；P1 只有 2 台机器，做不出真实拓扑
模型推理服务与 token 计费属于 P3；但账户与计费结构按 P3 预留
AI 自动调优 Agent见下方专门说明——不是 P1 需求，放进 P1 会挤掉计费工期
平台自身高可用2 台机器无法做主备；如实告知，不承诺 99.9%

"AI 自动调优 Agent" 的定位（请评审确认）

会议纪要中客户全程没有提过调优、Agent、自动化优化。客户的原话是"自动化调度与维护"，指的是资源按需分配和自动回收，属于 K8s 调度器的工作，不是模型层的参数或推理性能调优。这两件事名字像，工程量差一个数量级。

如果 P1 投入做 Agent：卡租不出去、账单算不对，客户第一阶段就跑不通，后面两阶段自然没有。建议这样处理：

  • P1 只做一个规则版"智能推荐"（≈3 人天）：根据历史占用推荐空闲卡、对掉卡和高负载节点做健康度打分。不叫 Agent，能演示、能讲故事。
  • 真正的调优 Agent 放到 P2，和多机场景一起做——那时才有真实的拓扑数据和 QoS 指标可优化。
  • 对客户的话术："自动化调度第一阶段就有；AI 调优要等多机跑起来才有数据，我们现在不拿 PPT 换你的预算。"

7 · 技术风险与对策

风险影响对策
5090 为消费级卡，无 ECC、无 MIG、驱动与企业卡不同高对外 SLA 按实际能力写，不承诺企业级可用性；掉卡告警必须做
2 台机器 = 平台单点，节点故障即全停高平台组件与卡池分离部署；如实告知，不写高可用承诺
计费与真实占用不一致（抢占、节点宕机、时钟漂移）高以"实例事件流"为唯一计费依据，而非定时采样；预扣 + 结算 + 每日对账三层兜底
资源回收不干净，卡被占死中Finalizer + 定时巡检强制回收，运维页可手动释放
对外经营算力租赁涉及资质中资质由客户侧解决，方案不承诺合规主体；合同口径需商务确认
单人 60 天满配排期，需求一变就崩中范围变更必须重算工期；每周固化一次可演示版本

8 · 需要客户确认的五个问题

  1. 2 台 5090 各装几张卡？是 16 卡还是 8 卡——直接决定可售算力与报价模型。
  2. 最小计费单位是什么？按小时还是按天；是否允许被抢占（允许则单价可降，但需在合同写明）。
  3. 实例是否需要公网访问？开放 SSH / Jupyter 到公网，还是只给内网 + VPN。这决定安全投入。
  4. 结算方式？预付余额实时扣，还是后付月结；开票主体是谁。决定计费模块的复杂度。
  5. 租户是谁？对外部客户经营，还是集团内部 / 关联方自用。涉及资质与合规口径。

附录 B · 硬件监控指标

全部由 GPU Operator 自带的 DCGM Exporter 采集，不自研采集器。RTX 5090 为消费级卡，下表中标注的字段能力需在 W1 实测确认。

指标DCGM 字段用途告警阈值
GPU 利用率DCGM_FI_DEV_GPU_UTIL判定卡是否闲置，影响能否超卖<5% 持续 30 分钟
显存已用 / 剩余DCGM_FI_DEV_FB_USED容量判断与 OOM 预警>95% 持续 10 分钟
温度DCGM_FI_DEV_GPU_TEMP降频与宕机预警>85°C 告警，>90°C 熔断
功耗DCGM_FI_DEV_POWER_USAGE电费成本核算长期贴近 TDP
降频原因DCGM_FI_DEV_CLOCK_THROTTLE_REASONS性能投诉归因（温度墙 / 功耗墙）非 0 持续 5 分钟
XID 错误DCGM_FI_DEV_XID_ERRORS掉卡识别，79 = 设备从总线掉落任何非 0 立即告警并摘卡
PCIe 吞吐DCGM_FI_PROF_PCIE_TX/RX_BYTES数据加载瓶颈长期打满
ECC 错误DCGM_FI_DEV_ECC_*—5090 不支持，跳过

5090 的三个硬性事实

  • DCGM_FI_PROF_* 类 profiling 指标在消费卡上大概率不可用，W1 需用 dcgmproftester 探测后再决定看板字段，避免大屏上一半是空图。
  • 不支持 MIG、不支持 vGPU、没有 NVLink。整卡独占是唯一形态，多卡通信走 PCIe——这一点需在 P2 多机场景前向客户说明。
  • XID 79 是消费卡高频故障。告警必须联动"把该卡标记为不可售并从池子摘除"，否则客户会租到坏卡。

整卡独占的说明

nvidia.com/gpu 是 Kubernetes 扩展资源，只能申请整数，因此 nvidia.com/gpu: 1 天然就是独占一张卡，不需要任何隔离配置。Volcano 在 P1 只承担两件事：租户队列配额、排队公平；gang scheduling 留到 P2。

本方案为技术评估稿，范围与工期基于 2026-10-30 售前交流信息。客户侧资源规格、计费口径、租户性质确认后需重新校准工作量。
